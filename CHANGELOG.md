# История изменений — Небосвод

Формат записи упрощённый, человеческим языком. Верхняя строка — последний исходящий релиз.

**Текущая версия:** 0.19.1 (2026-10-27)

---

## 0.19.1 — 2026-10-27
- **Восход и закат прижаты к низу краткой карточки** — карточка стала flex-колонкой, блок восхода/заката («☀ … ☾ …») прижат к низу (`margin-top: auto`), черта-разделитель едет вместе с ним. Карточки в ряду сетки выравниваются по самой высокой: даже у городов с длинными названиями или широкими температурами низ выглядит ровно.

## v0.19 — 2026-10-27
- **Температура со знаком «+»** — все положительные температуры (и ноль → без знака) отображаются с плюсом: карточки, модалка («Сейчас», «Сегодня», «Ночь», диапазоны «макс / мин»). Округление до целого — на клиенте (дробные из старого кэша тоже) и на сервере (округление стало математическим: 0.5 → 1 — как в JS; раньше Python-банкирское давало 0.5 → 0). API остаётся машинным — знак «+» только в интерфейсе.

## v0.17 — 2026-10-27
- **Таймер футера считает от серверного времени получения погоды** — batch-ответ `/api/weather?city_ids=...` дополнен полем `fetched_at` (unix-время получения самой свежей из отанных данных). Фронтенд считает «следующее обновление» от него, а не от момента ответа. Итог: **F5 больше не сбрасывает таймер** — сколько ни перезагружай страницу, отсчёт идёт от момента реального получения погоды сервером. «Обновлено: ЧЧ:ММ» теперь тоже показывает серверное время данных. Значение переживает перезагрузку страницы (localStorage).
- Проверено: два запроса подряд с интервалом 3 с возвращают одинаковый `fetched_at`; таймер после «F5» показывает 29:57, а не 30:00.

## v0.16 — 2026-10-27
- **Проверка и починка install/update-скриптов** (после реальных прогонов на тестовых контейнерах):
  - install: поддержка приватного git-сервера — `NEBO_GIT_TOKEN` добавляется к `NEBO_GIT_URL` на время клонирования и **не остаётся в origin** клона;
  - update: та же поддержка токена для `git fetch` (origin в контейнере не меняется);
  - update: разруливание незавершённого merge (конфликтные UU-файлы) перед stash — прежний прогон падал с «error: could not write index»;
  - update: если origin уже содержит креды (user:token@host) — токен не добавляется (раньше получался двойной токен в URL → Authentication failed);
  - server: **важный фикс** — запросы к IP-адресам fallback переводятся на `http://` даже при выключенном `open_meteo_http`: сертификат Open-Meteo выдан на имя, а не на IP (IP mismatch), без фикса свежая установка с пустым конфигом давала 502;
  - Рекомендация в README: для гарантии актуальной версии использовать `NEBO_GIT_URL` + `NEBO_GIT_TOKEN` (публичное зеркало GitHub может отставать).
- **Интервал автообновления страницы синхронизируется с сервером** — новый публичный эндпоинт `GET /api/config` отдаёт `background_refresh_minutes` и `cache_ttl`. Фронтенд при загрузке читает его и использует для своего таймера автообновления (раньше интервал 20 минут был зашит в `app.js` и рассинхронизировался при смене конфига). Если `/api/config` недоступен — fallback 30 минут.
- Дефолтный интервал обновления страницы теперь 30 минут (синхронно с рекомендованным серверным фоном).
- Документация: help.html обновлён («раз в 30 минут, страница подстраивается под конфиг сам»), README — описание `/api/config`.

## v0.15 — 2026-10-27
- **Авто-поиск резервных адресов Open-Meteo** (`open_meteo_discovery`, по умолчанию включён) — фоновый поток раз в 6 часов перебирает известные имена хостов Open-Meteo (`customer-api`, `customer-api-eu01..10`, `climate-api` и др.), проверяет найденные IP живым запросом прогноза (отсекая «пустышки» marine/air-quality) и обновляет ключ `open_meteo_fallback_hosts` в `config.json`: новые адреса добавляются, мёртвые удаляются (после проверки, не последним живым). При сбое DNS/сети конфиг не трогается. Изменения применяются без рестарта сервиса.
- **Равномерные чанки** — города делятся на запросы поровну, а не блоками: 70 городов при потолке 30 — не 30+30+10, а 24+23+23. Все запросы примерно одного размера, число запросов минимально. Потолок чанка настраивается (`open_meteo_http_batch_chunk`, по умолчанию теперь 30).
- **Sticky-хост** — адрес, который успешно ответил, запоминается и используется первым; при его отказе порядок мгновенно смещается. Нет лишних таймаутов на каждом запросе.
- **Новые боевые адреса**: найдены и проверены `climate-api` (5.9.98.12) и `customer-api` (138.199.128.119) — пул расширен с 2 до 4 живых forecast-бэкендов.
- Конфигурация: `open_meteo_discovery` (вкл/выкл авто-поиска), рекомендации по `background_refresh_minutes: 30` и `cache_ttl: 1800` (согласованные значения).
- Документация: README (авто-поиск, равномерные чанки, sticky), CHANGELOG, пример конфига.

## v0.14 — 2026-10-27
- **Fallback-хосты Open-Meteo** — новый ключ `open_meteo_fallback_hosts` (список IP или host:port). Если DNS отдаёт адрес, который провайдер глушит (случай боя 27.10.2026: TCP открывается, но и HTTP, и TLS висят до таймаута), сервис ходит на указанные адреса напрямую, подставляя заголовок `Host: api.open-meteo.com`. Если первый адрес не отвечает — автоматически пробуется следующий.
- **Проверка валидности ответа** — некоторые бэкенды Open-Meteo (air-quality, marine) отвечают на `/v1/forecast` статусом 200, но с пустыми данными (`temperature_2m: null`). Такой ответ больше не попадёт в кэш: попытка считается неудачной, и сервис пробует следующий адрес из списка. Раньше в кэш могли попасть «пустые» данные.
- Геокодинг (`geocoding-api.open-meteo.com`) на fallback-хосты не переносится: он живёт на других серверах Open-Meteo и работает штатно.
- Совместимость: ключ не задан — поведение не меняется; работает вместе с `open_meteo_http`.
- Документация: README (параметры, раздел о блокировках), пример конфига, отчёт о диагностике — `docs/FIX-open-meteo-block.md`.

## v0.13 — 2026-09-16
- **Обход блокировки Open-Meteo по SNI** — если провайдер глушит TLS к `api.open-meteo.com`, включается `"open_meteo_http": true` и запросы уходят по `http://` (работает и прогноз, и геокодинг). Причина выявлена на боевом сервере: рукопожатие с SNI=open-meteo зависает, с другим SNI проходит, а `:80` не блокируется вовсе.
- **Одиночные запросы при http-режиме** — http-фронтенд Open-Meteo не отдаёт большие пакетные ответы (5–40 городов виснут/503), поэтому с `open_meteo_http: true` города по умолчанию тянутся по одному (`open_meteo_http_batch_chunk`). Боевой сервер: 40/40 городов обновляются, прогрев и фоновое обновление работают.
- **Устойчивый прогрев** — каждый город пробует отдельно: сбой одного не останавливает остальные; перед стартом — пауза, чтобы сеть контейнера успела подняться. После цикла кэш целком записывается на диск (раньше троттлинг мог оставить неполный файл, и после рестарта часть данных пропадала). Проверено на двух рестартах подряд: 14/14 городов, файл полный.
- Конфигурация: новые ключи `open_meteo_http` и `open_meteo_http_batch_chunk` (по умолчанию `false`/`1` — поведение без правок не меняется).
- Документация: README и пример конфига описывают режим обхода и способ отката.

## v0.12 — 2026-09-16

## v0.11 — 2026-09-16
- **Кэш на диске** (`cache.json`) — переживает перезапуск сервиса. После рестарта страница открывается мгновенно: данные берутся из последнего сохранённого состояния, а не ждут Open-Meteo. Проверено: ответ после перезапуска — ~0,001 с.
- **Прогрев при старте** (`warmup_on_start`) — сразу после запуска сервис в фоне обновляет все города (пачками, одним запросом на 60 городов). Кэш заполняется сам, без захода пользователя.
- **Фоновое обновление** (`background_refresh_minutes`) — кэш тихо освежается по таймеру, поэтому данные не «остывают». `0` — выключить.
- **Stale-while-revalidate** — просроченные данные отдаются немедленно, а свежие подтягиваются в фоне. Больше нет ожидания внешнего источника при открытии страницы.
- Конфигурация: новые опции `warmup_on_start` и `background_refresh_minutes` (значения по умолчанию безопасны — старые конфиги работают без правок).
- Документация: README и страница помощи дополнены описанием кэша, прогрева и фонового обновления. В README появился подробный раздел о `config.json`: где он лежит, как его править, все параметры и поля городов, готовые примеры конфигов (минимальный, с несколькими городами, «максимально свежий», «тихий» режим).

## v0.10 — 2026-09-16
- **Пакетный запрос погоды** — `GET /api/weather?city_ids=1,2,3` отдаёт погоду для множества городов одним запросом (один вызов к Open-Meteo на всю пачку). Главная страница больше не делает по запросу на каждый город — при 40+ городах это в разы быстрее и заметно легче и для сервиса, и для браузера.
- **Stale-while-error** — если Open-Meteo недоступен, сервис не отдаёт ошибку и не оставляет пустые плитки: он показывает последние успешно полученные данные и помечает их как `stale` (в JSON — поля `stale`, `stale_age`; на плитке — метка «устарело»). Если данных нет вообще — только тогда честная ошибка.
- **Порядок плиток для зарегистрированных** — в настройках появился блок «Порядок плиток»: города расставляются стрелками ↑/↓, порядок сохраняется в базе (колонка `position` у `user_cities`) и применяется на главной. Миграция старых баз выполняется автоматически.
- **API списка городов** — `GET /api/all-cities` отдаёт все города сервиса (id, имя, alias, координаты, часовой пояс); работает как синоним `/api/cities`.
- Документация: в README и на странице помощи описаны пакетный запрос, список городов, поведение при недоступном источнике и настройка порядка плиток.
- Скрипт обновления: показывает список контейнеров и спрашивает ID, сам определяет каталог установки и имя сервиса.
